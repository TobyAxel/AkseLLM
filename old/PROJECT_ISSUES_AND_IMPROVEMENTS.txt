- `backend/Helpers/SupabaseHelper.cs`
- `backend/Helpers/HandleApiKeyHelper.cs`
- `backend/Controllers/*.cs`, `backend/Services/*.cs`

1) Missing containerization & deployment manifests for backend — HIGH
   - Issue: repository includes `frontend/Dockerfile` and `k8s/frontend/` but no backend Dockerfile nor k8s deployment/service.
   - Impact: harder to CI/CD, inconsistent deployment, onboarding friction; production rollout is blocked or manual.
   - Improvement: add a backend Dockerfile, build pipeline, and k8s manifests (Deployment, Service, Ingress). Include image tagging and readiness/liveness probes.

2) Supabase client & session handling per request — MEDIUM
   - Issue: `SupabaseHelper.GetClientAsync()` is called repeatedly in services, initializing a client each time.
   - Impact: connection/CPU overhead and possible connection leaks under load; inefficient resource usage.
   - Improvement: create a long-lived/DI-managed Supabase client or connection pool; reuse client instances and initialize them at app startup.

3) Generic exceptions & response mapping — HIGH
   - Issue: services throw generic `Exception("Invalid token")` and the `ExceptionFilter` maps unknown exceptions to 400 (BadRequest).
   - Impact: incorrect HTTP status codes, leaking internal messages to clients, and harder debugging/monitoring.
   - Improvement: use domain-specific exceptions (e.g., AuthenticationFailed, NotFound), map them to correct HTTP codes, and return minimal client-friendly messages; reserve 500 for unexpected server errors.

4) Secrets & configuration handling — MEDIUM
   - Issue: SUPABASE credentials are read from environment variables (good) but ensure `.env` isn't committed and DotNetEnv usage is not used in production deployment.
   - Impact: risk of secret leakage or inconsistent config across environments.
   - Improvement: centralize secrets into a secrets manager (Key Vault/Secrets Manager) and use environment-aware configuration. Add checks during CI to ensure no secrets are committed.

5) Authentication/session security and input validation — HIGH
   - Issue: controllers accept tokens from `Authorization` + `X-Refresh-Token` headers, but token validation relies on upstream SDK results; some service paths throw generic errors.
   - Impact: malformed inputs or missing validation can cause security or stability issues.
   - Improvement: centralize auth verification, validate DTOs at model-binding level, and enforce size/format/length limits for user input and model config.

6) Missing rate limiting & abuse controls — MEDIUM
   - Issue: no visible rate-limiting or request-throttling.
   - Impact: vulnerable to brute-force or DoS against LLM orchestration endpoints.
   - Improvement: add rate limiting (API gateway or middleware), request quotas, and auth throttles for critical endpoints.

7) Testing gaps — HIGH
   - Issue: no backend unit or integration tests detected.
   - Impact: regressions are hard to catch, lowering reliability and slowing development.
   - Improvement: add unit tests (xUnit/NUnit), integration tests for controllers (test server with in-memory config), and add test coverage thresholds in CI.

FRONTEND (files referenced)
- `frontend/src/services/api.ts`
- `frontend/src/services/authService.ts`
- `frontend/package.json`, `frontend/Dockerfile`

1) Token storage in `localStorage` — HIGH
   - Issue: `authToken` and `refreshToken` are persisted in `localStorage` by `authService` and read by `api.ts`.
   - Impact: high XSS risk (tokens accessible to injected scripts); refresh tokens in client storage increase account takeover risk.
   - Improvement: prefer secure HttpOnly same-site cookies for tokens or use rotating short-lived access tokens with refresh token rotation on the server. Minimize sensitive data exposed to JS.

2) Refresh handling & retry logic — MEDIUM
   - Issue: `api.ts` removes tokens on 401 but does not perform an automatic, safe refresh-and-retry flow.
   - Impact: poor UX and edge-case failures; potential for race conditions during token refresh.
   - Improvement: implement a single-flight token refresh flow with retry on access-token expiry, and fail-safe logout if refresh fails.

3) `any` usage and weak typing — MEDIUM
   - Issue: `catch (error: any)` and a few `any` usages (e.g., `handleAuthSubmit` signature) reduce type-safety despite `strict` TS.
   - Impact: prevents compile-time checks, increases runtime errors and developer friction.
   - Improvement: tighten types, avoid `any`, add helper types for API responses, and enable additional ESLint rules to catch `any` usage.

4) Missing frontend tests & e2e — HIGH
   - Issue: no unit tests for components or e2e tests for flows.
   - Impact: regressions in UI and auth flows may go unnoticed; deployment risk increases.
   - Improvement: add unit tests (React Testing Library + Vitest/Jest) and add an e2e suite (Playwright/Cypress) covering auth and LLM CRUD flows.

5) Security headers & static hosting hardening — MEDIUM
   - Issue: `frontend/Dockerfile` serves `dist` with plain nginx; no CSP/HSTS headers.
   - Impact: weaker protection against XSS/Clickjacking in production.
   - Improvement: configure nginx to add security headers (CSP, HSTS, X-Frame-Options, Referrer-Policy) and serve with TLS at ingress.

6) Accessibility (a11y) checks — LOW
   - Issue: some components have ARIA but no systematic accessibility validation found.
   - Impact: potential accessibility regressions.
   - Improvement: run an a11y audit, add eslint-plugin-jsx-a11y, and include keyboard & screen-reader tests in CI.
